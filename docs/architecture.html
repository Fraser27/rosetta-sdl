What happens when no metric matches?

In _handle_structured() (routes_query.py:208), if disambiguate() returns no metric (or the compiled metric is invalid), the pipeline falls back to LLM SQL generation:

  1. generate_sql(question, disambiguation, graph, bedrock.query_model) — the LLM writes SQL grounded in the real schema pulled from the graph. This is ungoverned — the SQL is not deterministic and not from a curated metric.
  2. The result still passes through the SQL firewall (routes_query.py:212) — ungoverned does not mean unguarded.
  3. Execution uses the legacy Athena executor (athena_execute_query), not a datasource-resolved executor, because there is no metric → no EXECUTES_ON binding. Response is tagged query_type: "ungoverned", intent: "analytical".

Contrast: a governed match compiles deterministic SQL (no LLM) and routes to the metric's bound datasource engine. An ungoverned miss uses the LLM and defaults to Athena.

2. When is the SQL firewall invoked?

SQLFirewall.validate(sql) (src/query/firewall.py) runs on every path that executes SQL, immediately before execution. It parses SQL with sqlglot (Trino dialect) and denies any table not in the allowlist. It also excludes CTE names (they're internal aliases) and inspects subqueries/CTEs/UNIONs for real table refs.

Firewall modes (env FIREWALL_MODE)

  • catalog (default) — allowlist is the set of tables known to the graph, resolved lazily on each validate() (30s cache), so tables added by a scan become allowed automatically.
  • explicit — only config.allowed_tables.
  • disabled — allow everything (logs a loud warning; the ONLY way to bypass).

Security invariant: an empty allowlist denies all (fail-closed) — it is never a silent no-op.

3. The Neo4j ontology — nodes, properties, relationships

Two conceptually different :DataSource nodes coexist: a Glue-database node (keyed by name, created during scan, CONTAINS tables) and an executor datasource node (keyed by datasource_id, e.g. ds_default_athena, PROVIDES tables and is the EXECUTES_ON target for metrics).

4. Vectors — what's stored, and where

There are two separate vector stores, used for two different purposes:

Metric embeddings → in Neo4j

  • Stored on the Metric node as the embedding property (SET_METRIC_EMBEDDING).
  • Model: Titan amazon.titan-embed-text-v2:0, 1024 dims, cosine similarity.
  • Indexed by a Neo4j vector index metric_embedding (src/graph/schema.py:54), created FOR (m:Metric) ON (m.embedding).
  • Used by route_query/disambiguate as a fallback when full-text metric matching is weak — i.e. to decide "does this question map to a governed metric?".
  • Embedding text = name + definition + synonyms (build_metric_embedding_text).

Document embeddings → in S3 Vectors

  • The Neo4j Document node does NOT store the embedding. It stores only pointers: vector_bucket and vector_index.
  • Actual document vectors live in Amazon S3 Vectors buckets/indexes (external to the graph).
  • search_vectors() reads the bucket/index from Document nodes, embeds the question (Titan), then calls the S3 Vectors query_vectors API for kNN.
  • This is the unstructured path — semantic document retrieval, not SQL aggregation.

Full-text indexes (Neo4j, for routing/disambiguation)

table_search, column_search, metric_search, document_search, business_term_search (src/graph/schema.py). These drive the first-pass keyword routing before the metric vector fallback kicks in.

5. End-to-end summary

  • Governed question → matched Metric → deterministic compile_metric SQL → firewall → executor bound via EXECUTES_ON (Athena/Redshift).
  • No metric → LLM generate_sql (ungoverned) → firewall → legacy Athena.
  • Document question → search_vectors → S3 Vectors kNN (no SQL, no firewall).
  • Firewall guards every SQL execution; fail-closed by default; catalog-derived allowlist; CTE-aware.
  • Graph stores the semantic model (metrics, tables, columns, joins, datasources, documents); metric embeddings live on the node; document embeddings live in S3 Vectors and the node only points to them.
